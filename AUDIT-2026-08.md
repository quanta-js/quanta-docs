# quanta-docs — Audit Findings (2026-08)

Companion to `ANALYSIS-v2.md` in [`quanta-js/quanta`](https://github.com/quanta-js/quanta), which covers the library itself.
This file covers the documentation site only.

---

## 1. Security

### D-1 (Medium) — Unvalidated path join in the raw-MDX API route

`app/api/docs/raw/[[...slug]]/route.ts` passes user-controlled URL segments straight into a filesystem read:

```ts
const slug = params.slug?.join("/") || "";
const rawMdx = await getRawMdxForSlug(slug);
```

which lands in `lib/markdown.ts`:

```ts
function getDocsContentPath(slug: string) {
    return path.join(process.cwd(), "/contents/docs/", `${slug}/index.mdx`);
}
```

`path.join` resolves `..`, so the read can escape `contents/docs/`. Practical impact is limited — the hardcoded `/index.mdx` suffix
constrains what is reachable, and Next.js normalises many traversal attempts before routing — but this is an unvalidated path join
(CWE-22) on a public endpoint.

**Fix.** Either resolve and fence the path:

```ts
const root = path.resolve(process.cwd(), "contents/docs");
const target = path.resolve(root, slug, "index.mdx");
if (target !== root && !target.startsWith(root + path.sep)) return null;
```

or, better, allowlist `slug` against the existing `page_routes` table in `lib/routes-config.ts` — the set of valid docs paths is
already known statically.

`getAllChilds` and `getBlogForSlug` build paths the same way and deserve the same treatment.

## 2. Correctness / dependency hygiene

### D-2 (Medium) — `@quantajs/*` dependencies are unpinned

```json
"@quantajs/core": "latest",
"@quantajs/react": "latest",
```

`latest` means the docs site's build output changes without a commit, and a bad publish breaks the site with no bisectable cause.
Pin to an exact version and bump deliberately — the docs site is the library's most important integration test.

### D-3 (Low) — Self-referencing dependency

`"quanta-docs": "file:"` in `dependencies` refers to the package itself. Remove it.

### D-4 (Medium) — No CI

There is no `.github/workflows` in this repo. A docs site is the first thing a prospective user touches; it should at minimum run
lint, a production build, and a broken-link check on every PR. Add a job that also builds against the **pinned** `@quantajs/*`
versions so a library regression fails the docs build loudly.

## 3. The demo stores are teaching around library bugs

`components/persistence-demos/stores/index.ts` is the file people will copy from. It currently contains:

```ts
updateQuantity(productId: number, quantity: number) {
    // ...
    this.items = [...this.items]; // Reassign for array reactivity
}
```

That comment is a public admission that in-place array mutation does not propagate. It is caused by library defects **B-1** (selector
identity comparison) and **B-6** (new keys don't invalidate enumeration deps) in `ANALYSIS-v2.md`. A developer evaluating QuantaJS
will find this within five minutes and draw the obvious conclusion.

**Action:** fix B-1/B-6 in the library, then delete the workaround and the comment.

Two more anti-patterns in the same file:

- **`total` is manually-synced state.** It is recomputed by hand in `updateTotal()` and called from four places. It should be a
  getter — the store already has a `getters` block right above it. As written, the canonical example demonstrates the exact
  derived-state-drift bug that getters exist to prevent.
- **Module-scope adapter construction will throw during SSR.** `new LocalStorageAdapter("user-preferences")` runs at import time, and
  its constructor throws when `window` is undefined. `'use client'` modules still execute on the server during Next.js SSR. This is
  the SSR gap described in §6.7 of `ANALYSIS-v2.md`, demonstrated live on your own site. Until the library ships SSR-safe adapters,
  these stores need lazy initialisation.

## 4. Documentation gaps to close

Ordered by how often the underlying question comes up in the wider ecosystem:

1. **An SSR / Next.js App Router page that actually works.** Hydration mismatch with persisted state is the most-blogged-about
   breakage in this ecosystem. Right now the site's own demos would hit it.
2. **A "choosing QuantaJS" page** with an honest comparison against Zustand / Jotai / Valtio / Pinia, including where *not* to use it.
   Developers trust libraries that name their own limits.
3. **A performance guide** covering subscription granularity and how to avoid whole-store re-renders — with a measured before/after,
   not prose.
4. **A security page** for the persistence layer: what gets written to localStorage by default (currently: *everything*), how to
   redact secrets, and the cross-tab trust model.
5. **A testing guide.** "How do I reset stores between tests?" is a first-week question and the current answer (`$destroy()` plus
   unique names) is not discoverable.
6. **Migration + upgrade notes per minor**, and a documented deprecation policy. This is what enterprise adopters actually check.
7. **A live playground** (StackBlitz/Sandpack embeds). The single highest-conversion element a state-library site can have.

---

## 5. Performance of the site itself

The landing page loads three.js, `@react-three/fiber`, `@react-three/drei`, gsap, `@tsparticles/*` and `motion`. A library whose
headline claim is "blazing fast" is judged on its own Lighthouse score before anyone reads a benchmark. Consider deferring the 3D
scene behind an intersection observer, or dropping it — and publish the Core Web Vitals on the homepage as a statement of intent.
